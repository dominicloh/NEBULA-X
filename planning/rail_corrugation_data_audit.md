## 5. Signal meanings and units (from the Info Kit, Section 2.1)

| Column(s) | Meaning | Unit / notes |
|---|---|---|
| `Rotating speed` | Output of a toothed-wheel speed sensor (90 teeth around the wheel circumference); toggles between 1 and 0 as teeth pass a detection point. Train running speed is derived by counting 0/1 transitions over time. Wheel diameter = 0.85 m. | Raw sensor toggle signal (0/1), not already-converted to km/h in the file. |
| `Vibration of bearing in position N of car C` | Axle-box vertical acceleration at that position, from an accelerometer. | m/s² |
| `Shock of bearing in position N of car C` | Axle-box shock/impact reading at that position. | m/s² (per Info Kit, same unit stated for "vibration and shock data") |

- The train has **8 cars × 8 axle-box positions = 64 sensor locations**, each with a vibration and a shock channel (64 × 2 = 128 signal columns + 1 speed column = 129).
- **Side mapping (confirmed)**: positions **1, 3, 5, 7** = Side I rail; positions **2, 4, 6, 8** = Side II rail. This mapping is the same for every car.

## 7. Meaning of the three labels (from the Info Kit, Section 2.2)

| Label | Meaning |
|---|---|
| `Normal` | Both Side I and Side II rails are normal (no corrugation on either side). |
| `Side I` | Corrugation present on the Side I rail; Side II rail is normal. |
| `Side II` | Corrugation present on the Side II rail; Side I rail is normal. |

Important nuance stated explicitly in the Info Kit: **Side I and Side II must be judged independently from the same recording** — a file can show a fault on one side while the other side is normal. The final label is a joint 3-class outcome of two per-side judgments, not two independent binary labels reported separately.

## 11. Modelling implications

- **Severe class imbalance** (86% / 8.8% / 5.1%) means:
  - A stratified train/validation split (by file, preserving class ratios) is necessary — a random split risks a validation fold with zero or near-zero Side I examples.
  - Class weighting, resampling, or a macro-F1-aware threshold/decision strategy should be considered during modelling (not this stage) since the metric explicitly penalises collapsing to the majority class.
  - With only 14 Side I examples total, k-fold cross-validation (rather than a single hold-out split) is likely necessary to get a stable macro F1 estimate.
- **Each file is one 1-second, 10,000-sample, 129-channel recording that must reduce to a single 3-class label** — this is a file-level (not row-level) classification problem, so features must summarize the full 10,000-row window per file (e.g. time-domain and frequency-domain statistics per channel), not be computed row-by-row.
- **Side-aware feature design is implied by the Info Kit**: since positions 1/3/5/7 (Side I) and 2/4/6/8 (Side II) are separately meaningful, features should likely be aggregated per side (e.g. across all 8 cars' Side I positions vs. all 8 cars' Side II positions) rather than treating all 64 positions as one undifferentiated group — this preserves the side-localisation signal the labels depend on.
- 129 raw columns × 10,000 rows per file is too large to feed a classical model directly without feature engineering (272 training files is a small sample count relative to raw dimensionality) — file-level summary features are the natural next step, not raw-sequence modelling, given the small file count.
- The Rotating speed channel is a raw 0/1 toggle signal, not a pre-computed speed value — turning it into an actual speed (km/h or m/s) would require decoding the 90-tooth transition counting described in the Info Kit; whether this is needed as a feature (e.g. to normalise vibration by operating speed) is a design decision for the modelling stage, not resolved here.

## 13. Recommended next modelling step

1. Design a stratified (by class) cross-validation split at the **file** level — e.g. Stratified K-Fold — given the 14/24/234 class sizes, so every fold contains at least a few Side I and Side II examples.
2. Build **file-level summary features per channel** (e.g. mean, std, RMS, peak, and a few frequency-band energy features per vibration/shock column), aggregated separately for the Side I position group and the Side II position group, as motivated in Section 11.
3. Train a baseline classifier (e.g. a tree ensemble such as Random Forest or Gradient Boosting) with **class weighting** on top of these features, and evaluate with **macro F1** via the CV split from step 1 — matching the official metric from the first baseline onward rather than optimising accuracy and switching later.
4. Only after a baseline macro F1 is established should further feature engineering, model tuning, or the `predict.py`/app integration begin (all explicitly out of scope for this stage).
